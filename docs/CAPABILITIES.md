# UPF-Insight — Capabilities

> **Version:** v0.3.0 · commit `3ffa0b2` · tag `v0.3.0-validation.1`
> **Read with:** [`docs/validation/REAL_WORLD_REPORT.md`](validation/REAL_WORLD_REPORT.md)
> — the limits below are measured, not aspirational.

---

## What it is

A deterministic, local-first validator for IEEE 1801 (UPF) power-intent files.
No EDA tool, no LLM, no network. It parses UPF, builds an object graph, runs 77
rules, and reports findings that each trace to a `file:line`.

It is the **power-intent sibling** of Ṛta / sdc-tools (the SDC validator).

## What it does well

### Semantic power-intent checks — the core value

These fire correctly on real-world UPF and catch the failures industry
low-power checklists call "silently lethal":

| Area | Rules | What it catches |
|---|---|---|
| Isolation | UPF-040…047 | Crossing coverage, missing `-applies_to inout`, clamp values, control-signal always-on |
| Level shifter | UPF-060…064 | Shifters where voltages match, missing ones where they differ, always-on control |
| Retention | UPF-050…054 | Retention supply, save/restore control, always-on confirmation |
| Repeater | UPF-090…094 | Repeater supply, control, location, domain placement |
| PST | UPF-030…038 | Missing tables, unreachable states, switch/PST contradictions, strategies with nothing to condition them on |
| Power state cross-checks | UPF-037 | Domain powers down while a receiver stays on, with no active isolation |
| Wildcard risk | UPF-087 | Low-specificity `reg*`-style element patterns that mask real elements |

Each finding carries a **support status** — `VALIDATED`,
`PARTIALLY_VALIDATED`, `NETLIST_REQUIRED`, `TCL_EXECUTION_REQUIRED`,
`UNSUPPORTED`, `NOT_VALIDATED` — so a check that could not be completed never
reads as a pass. This is the project's central discipline: *"no errors" ≠
"power proven correct."*

### Structural analysis

- **Model** — 77 rule-backed entities across 7 layers (STRATEGY 36, PST 10,
  REFERENCE 10, DESIGN 8, SYNTAX 6, SUPPLY_DOMAIN 6, SUPPLY 1)
- **Semantic diff** — compares two built models, ignoring provenance fields, so
  reformatting never produces a false MODIFY
- **Readiness** — aggregate verdict (READY / READY+ / REVIEW_REQUIRED /
  BLOCKED / INSUFFICIENT_CONTEXT) across seven power-intent dimensions
- **Domain relation graph** — supply sharing, switch mapping, crossing matrix
- **Coverage & interactions** — strategy-vs-PST coverage, strategy conflicts
- **Generator** — flat and hierarchical UPF skeletons, round-trip tested
- **Bounded local API + web UI** — stdlib-only HTTP server, loopback-bound

### Determinism

Same input → byte-identical output. Verified: rule ordering is sorted by code,
hash-order is never allowed to leak into results, and `check` run twice
produces identical JSON. The registry/handler join is asserted exactly equal
(77/77) by an audit test.

## What it does not do — measured limits

### 1. The parser does not yet read real-world UPF (44% FP on shipped corpus)

The engine validates **its own dialect**. A file generated by UPF-Insight's
generator scores 0 errors; the same design hand-written in legal IEEE 1801
scores 12, nearly all spurious.

Root cause: the accepted-option grammar is narrower than the standard, and
brace groups are not expanded. Full breakdown and per-defect analysis in the
validation report.

**Practical consequence:** do not gate CI on this tool until the P0 items in
the validation report are closed. A gate that fails for phantom reasons gets
switched off, and then it protects nothing.

### 2. No netlist = no crossing verification

Isolation/LS/retention checks are **declared-strategy vs domain**. Without a
netlist the engine cannot know which signals actually cross, so it cannot say
*"these 14 signals reach PD_AON with no strategy"* — only *"you declared
isolation for PD_CPU."* Those checks report `NETLIST_REQUIRED`, honestly, but
they are the difference between a useful tool and a rubber stamp. Netlist and
Verilog readers exist (`--netlist`); the endpoint-based coverage computation
that would use them is not implemented (UPF-082/083 are stubs).

### 3. Tcl is detected, never executed

`source`, `exec`, and variable substitution are **reported, not resolved**.
Designs relying on Tcl to build power intent get a `TCL_EXECUTION_REQUIRED`
boundary, not a model. This is deliberate — deterministic and sandboxed — but
it is a hard ceiling on input variety.

### 4. No physical, timing, or power analysis

Out of scope by design: no IR drop, EM, STA, DRC, LVS, LEC, or power
estimation. UPF-Insight validates **declared intent**, never implemented
behavior.

### 5. Known modelling gaps

Verified and recorded rather than hidden:

- `differ.py` compares strategies **count-only** — content changes inside a
  strategy are not detected
- `record_files` is keyed by **line number alone**, so two files with commands
  on the same line are ambiguous (consumers return "no file" rather than
  guessing — honest, but weaker provenance than it appears)
- `analyze_pst` analyzes the **first** PST only
- `create_supply_net -resolve`, `create_supply_port -domain`, `create_pst
  -supplies` are accepted then discarded
- `add_power_state` is deliberately **not modeled** — deprecated in IEEE 1801,
  correctly reported by UPF-005 (intentional, not an oversight)

## Command surface

```
upf-insight check FILE...        # validate; --format text|json|junit
upf-insight model FILE...        # emit the object graph
upf-insight pst FILE...          # power-state table analysis
upf-insight coverage FILE...     # coverage gaps
upf-insight relations FILE...    # domain relation matrix
upf-insight analyze FILE...      # one-shot end-to-end + HTML report
upf-insight diff OLD NEW         # semantic diff
upf-insight generate             # scaffold flat or hierarchical UPF
upf-insight rules list|show|audit# rule registry
upf-insight quality              # mutation corpus self-check
upf-insight batch check DIR      # directory sweep
upf-insight lint|convert FILE    # style + format conversion
upf-insight web                  # local workspace UI
```

Exit codes: `0` pass · `1` gate failed · `2` invalid invocation · `3` engine
failure. `--gate`/`--baseline` apply policy to CI pipelines.

## Evidence quality

| Property | Status |
|---|---|
| Test suite | 309 passing (no xfail remaining) |
| Mutation corpus | 42/42 seeded defects detected (100% recall) |
| Mutation precision | **0.57** — the engine fires on 43% of its own findings |
| Real-world FP rate | **0%** on `tests/corpus/` (0 of 21); all 21 findings are genuine / needs-review |
| Registry/handler parity | exact, audit-clean |
| Determinism | byte-identical on repeat runs |

Recall is excellent; **precision on the shipped corpus is now clean.** The
caveat worth stating plainly: 0% is measured on the two files in
`tests/corpus/`, one of which we wrote ourselves to cover legal option
spellings. The external open-source projects measured in
`docs/validation/REAL_WORLD_REPORT.md` (65% at v0.3.0) have not been
re-measured — that UPF is not redistributed here. Those defects have been
fixed at the grammar, so 65% is a historical upper bound rather than a current
claim, but confirming it means re-running those corpora.

Recall is excellent; **precision is the remaining weakness**, and the evidence
for that is now confined to the mutation corpus (0.57) and the un-re-measured
external projects.

## Who should use it

**Yes, for:** exploring a UPF file quickly; learning what a power intent
actually declares; finding semantic issues (crossing coverage, always-on
controls, PST contradictions) in a file you control; CI reporting once the
parser gaps are closed.

**Not yet, for:** gating a real project; any flow where a false error costs a
designer's trust; design-aware verification requiring netlist crossing
analysis.
