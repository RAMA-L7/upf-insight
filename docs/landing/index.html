The Problem
Power intent fails silently
Before power-aware implementation, UPF problems are expensive to find. Domains, supplies, switches, and strategies may each look valid in isolation while the complete system remains broken.

Fragmented validation

Most tools check UPF commands in isolation. A switch looks valid. An isolation strategy looks valid. But the relationship between them goes unchecked.

Late detection

Power-intent errors found during place-and-route are expensive. A missing level shifter at RTL review costs minutes. At tapeout, it costs weeks.

No regression protection

UPF files evolve across design versions. Without semantic diffing and CI gating, validated power intent can silently regress.

PST complexity

Power State Tables encode legal power combinations across supply networks. Manual verification — especially with power switches — is error-prone.

Finding Explanation
Every finding traces to evidence
Not just an error code — the semantic relationship, why it matters, and what to fix.
UPF-062 ERROR Wrong level-shifter rule
Level shifter ls_core is declared as high_to_low, but CORE (0.8V) → IO (1.0V) is a low-to-high voltage crossing.
CORE 0.8V ─────────────► IO 1.0V LOW → HIGH Declared: high_to_low ✗ Required: low_to_high ✓
Fix: Change -rule high_to_low to -rule low_to_high
UPF-039 ERROR Impossible PST state
PST state declares VDD = OFF but VDD_SW_OUT = ON. Power cannot appear downstream when the switch input is OFF.
VDD ──► SW_CORE ──► VDD_SW_OUT OFF ON ← impossible Power cannot materialize from nowhere.
Fix: Set VDD_SW_OUT = OFF when VDD = OFF, or remove the state.

Developer
CLI-first. API-ready.
Both upf-insight and upfi work interchangeably. Machine-readable JSON for CI. Local workspace for interactive analysis.
# validate a UPF file
upf-insight check soc.upf

# machine-readable output for CI
upf-insight check soc.upf --format json

# dump the power-intent model
upf-insight model soc.upf -o model.json

# analyze the Power State Table
upf-insight pst soc.upf

# semantic diff between two versions
upf-insight diff soc.v1.upf soc.v2.upf

# scaffold a power-intent skeleton
upf-insight generate --domains core,io,sram --retention core

# gate changes in CI
upf-insight check soc.v2.upf --baseline baseline.json --gate STRICT

# produce a report
upf-insight report soc.upf -o report.html

# launch the workspace (local, offline)
upf-insight web

01UPF Validation
core▸
Deterministic IEEE 1801 (UPF) validation with per-finding source provenance. Every finding traces to a specific line in the UPF source. Rules span 6 layers: syntax, reference, supply/domain, PST, strategy, and design-aware.
$ upf-insight check soc.upf $ upf-insight check soc.upf --format json $ upf-insight check soc.upf --rule UPF-040 --rule UPF-061
Rules: UPF-001 through UPF-100 · 74 rules · 6 layers
02Power-Intent Model
core▸
Builds a complete object graph from your UPF: domains, supplies, switches, states, PST, and strategies. Queryable from CLI or API.
$ upf-insight model soc.upf -o model.json
Output: domains, supplies, switches, states, strategies, relations, provenance
03Power State Table Analysis
core▸
Expands and analyzes the PST for consistency. Detects impossible states (UPF-039), undeclared states, missing PST, empty states, duplicate states, and un-isolated power-down crossings.
$ upf-insight pst soc.upf
Rules: UPF-030 through UPF-039 · PST layer
04UPF Generator
core▸
Scaffold power-intent from architecture parameters. Supports flat and hierarchical designs with per-child domain ownership, domain types, switches, isolation, level shifters, retention, and relations. Generated UPF validates back through the same engine — full round-trip.
# Flat generation $ upf-insight generate --domains core,io,sram --retention core # Hierarchical generation $ upf-insight generate --architecture hierarchical \ --hierarchy core_a,core_b \ --domain-type core_a:switchable \ --switch sw_a:core_a:vdd_aon:vdd_a:pg_en \ --relation core_a:sram:isolation,level_shift
Output: complete UPF 3.0 file with domains, supplies, switches, strategies, PST
05Semantic Diff
analysis▸
Compares two UPF versions semantically — not textually. Classifies changes as ADD, REMOVE, or MODIFY across domains, supplies, switches, strategies, and states.
$ upf-insight diff soc.v1.upf soc.v2.upf
Output: ADD / REMOVE / MODIFY per object with source line provenance
06CI Quality Gate
ci▸
Policy-based CI gating with three modes: BLOCKERS_ONLY, NO_READINESS_REGRESSION, and STRICT. Exit codes: 0 pass, 1 issues, 2 invalid, 3 engine failure.
$ upf-insight check soc.v2.upf \ --baseline baseline.json --gate STRICT
Policies: BLOCKERS_ONLY · NO_READINESS_REGRESSION · STRICT
07HTML / JSON Reports
output▸
Generates reports from real analysis evidence — not template text. HTML reports include finding tables, supply topology, statistics, and source provenance.
$ upf-insight report soc.upf -o report.html
Formats: HTML · JSON · text
08Domain Relation Matrix
analysis▸
Cross-domain interaction matrix showing ISO / LS / ISO+LS / RET / SW / CTRL relationships. Each cell has provenance.
$ upf-insight relations soc.upf
Output: relation matrix + supply network graph

15Finding Dependencies
architecture▸
Cascade-aware finding system. Root causes block dependent findings. When UPF-010 fires, UPF-070 is downgraded to BLOCKED.
# Automatically applied — no flag needed $ upf-insight check soc.upf # UPF-010: ERROR (root cause) # UPF-070: BLOCKED (dependent on UPF-010)
Mechanism: depends_on tuples in rules_registry.py
